# Technical Decisions

This document records major technical decisions for IRIDIUM. It helps reviewers and future contributors understand tradeoffs and constraints.

## Stack and Layout

- **Backend**: Python 3.12, FastAPI. Chosen for rapid development, strong typing (Pydantic), and automatic OpenAPI. Suitable for research-heavy and API-first workloads.
- **Frontend**: React, TypeScript, Vite. Chosen for a single-page dashboard, type safety, and simple build. No heavy framework to keep the baseline maintainable.
- **Schemas**: Pydantic in `packages/schemas`; shared between API and services. Single source of truth for request/response and ingestion contracts.
- **Monorepo**: Apps (api, web), packages (schemas, config), and services (ingestion, digital-twin, forecasting, routing, equity, anomaly-detection) live in one repository. Simplifies contract alignment and local development.

## Digital Twin

- **Current**: In-memory graph (nodes, edges) with optional state overlay. No persistence. Enables runnable demos and tests without a database.
- **Rationale**: Proves the concept and API surface; persistence can be added behind the same service interface.
- **Future**: PostgreSQL with optional PostGIS; schema in `infrastructure/db/schema.sql`. Ingestion would write into the twin store.

## Forecasting

- **Current**: Heuristic baseline (current twin state plus temporal decay). No trained model.
- **Rationale**: Demonstrates the forecast API and pipeline; avoids claiming accuracy without evaluation. Extension point for ST-GNN is explicit.
- **Future**: ST-GNN (e.g. PyTorch Geometric) trained on historical or synthetic data; model versioning and evaluation per research/evaluation-plan.md.

## Routing

- **Current**: Weighted path search on the digital twin graph. Origin/destination snapped to nearest nodes. Objectives: time, cost, carbon.
- **Rationale**: Shows multimodal optimisation and API; not a full journey planner. Schedule-based transit and real-time weights are planned.
- **Future**: Full multimodal graph with schedules, transfer penalties, and real-time edge weights from the twin.

## Federated Learning

- **Current**: Not implemented. Architecture and documentation only.
- **Rationale**: Correct protocol design and security assumptions require dedicated effort; the baseline focuses on the digital twin, APIs, and local services.
- **Future**: Orchestration (e.g. Flower), secure aggregation, and participant client; documented in docs/federated-learning.md.

## Data and Privacy

- **Current**: No raw personal data in the repository. Schemas do not define fields that identify individuals or devices. GNSS and telemetry are assumed aggregated or anonymised at source.
- **Rationale**: Public repo must not contain or imply central storage of personal mobility data. Federated design supports future privacy-preserving deployment.
- **Synthetic data**: All included data is synthetic or illustrative. See data/synthetic/README.md and docs/demo-scenario.md.

## API Design

- **Versioning**: Prefix `/api/v1/` for domain routes; `/health` and `/version` at root. Breaking changes will introduce a new version path.
- **Errors**: HTTP status codes and JSON detail. No stack traces or sensitive data in responses. Structured error schema can be added for consistency.
- **OpenAPI**: Generated by FastAPI from Pydantic models. Served at `/docs` and `/redoc`.

## Testing and CI

- **Tests**: Pytest for backend (unit and integration via TestClient); Vitest for frontend. No E2E or load tests in the baseline.
- **CI**: Lint, format, and test workflows; continue-on-error where optional (e.g. missing frontend deps). Realistic for an early-stage repo.
- **Rationale**: Confidence without over-engineering; CI can be tightened as the team grows.

## What We Explicitly Did Not Do

- **Production deployment**: No claim of production readiness, SLAs, or scaling guidance beyond Docker Compose.
- **Legal compliance claims**: Privacy and federated learning are design choices; deployers are responsible for compliance.
- **Real data or benchmarks**: No real city data, no published accuracy numbers, no comparison to external systems.
- **Heavy ML infrastructure**: No training pipelines, experiment tracking, or model registry in the baseline.
